# Idempotency

An operation is idempotent when performing it repeatedly
has the same effect as performing it once. It is the
single property that makes retries, redelivery and
replays safe, and therefore the foundation under half of
[[Failure Modes]].

## Which operations already have it

| Operation | Idempotent? |
|---|---|
| `GET /orders/42` | Yes |
| `PUT /orders/42` with the full body | Yes |
| `DELETE /orders/42` | Yes (second call: still deleted) |
| `POST /orders` | **No** — creates another order |
| `UPDATE t SET n = n + 1` | **No** |
| `UPDATE t SET n = 7` | Yes |
| Sending an email | **No** |
| Charging a card | **No** |

The interesting cases are all in the "no" column, and
they are the expensive ones ([[HTTP]] defines the first
group; the rest is your problem).

## The idempotency key

Give each *attempt at a distinct intention* a stable ID,
generated by the caller before the first try and reused
on every retry. The server records the key with the
result:

- **First request with key K** — do the work, store
  `K -> result`, return it.
- **Repeat with key K** — return the stored result
  without doing the work again.
- **Repeat with K while the first is in flight** — return
  409, or wait. Do not start a second one.

```sql
CREATE TABLE idempotency (
  key         text PRIMARY KEY,
  response    jsonb,
  created_at  timestamptz DEFAULT now()
);
```

The unique constraint is what makes this correct: two
concurrent workers race, one inserts, the other gets a
conflict and knows the work is taken. An `if exists`
check in application code does not do that.

[[Stripe]] and most payment APIs accept an
`Idempotency-Key` header for the same reason. Use it —
generate the key when the user clicks, not when the
request is sent, so a client retry reuses it.

## Where the key should come from

**The producer, not the consumer.** A consumer that
generates the key on receipt will generate a different
one for a redelivery, which defeats the whole mechanism.
Natural keys are best when they exist: an order ID, a
webhook event ID, `(user_id, date)` for a daily digest.

## Making a handler idempotent

1. Derive or accept a stable key.
2. In **one transaction**, insert the key and apply the
   effect. If the insert conflicts, roll back and return
   the previous result.
3. For effects outside the database (email, payment,
   third-party API), pass the key through so that side
   is deduplicating too.
4. Expire old keys — 24 hours to 7 days is typical.
   Retries do not arrive a month later.

## Watch out for

**Partial idempotency.** A handler that writes a row
idempotently but sends the email outside the transaction
is not idempotent; the user gets two emails. The effect
users can see is the one that has to be covered.

**Idempotent is not commutative.** Two different updates
that each arrive twice can still interleave into a wrong
final state. If order matters, you need versioning or
sequencing as well — check a version number and reject
stale writes.
